# YOLOv5、TensorRT INT8 与多传感器映射方案

日期：2026-10-27。状态：用户已批准方案 A，v0.3 已完成本地实现与验证；本文保留设计时的范围说明。最终使用方式见 `../../int8-and-mapping.md`，实际验证边界见 `../../v03-verification.md`。

用户已安装 Jetson 系统，后续将提供摄像头、海拔和毫米波雷达数据。本次目标是为 YOLOv5 分割增加真实的 TensorRT INT8 部署流程，并建立可校验、可回放的传感器映射链路。

## 现状核查

- 项目为 FastAPI + 原版 YOLOv5 分割适配器，支持 `.pt` 与带类别元数据的 `.engine`。
- 当前 `scripts/export_yolov5_engine.py` 只请求 FP16。固定版本 YOLOv5 的 `export_engine()` 没有 INT8 参数；顶层 `--int8` 用于其他导出格式，不能作为 TensorRT INT8 已实现的证据。
- `POST /v1/weed-segmentation` 已返回像素框、真实掩膜面积、中心点和轮廓；地面坐标始终为 `null`。
- `detections_from_result()` 当前转换后丢弃二值掩膜。精确的雷达点与分割区域关联需保留短期内部掩膜；不能依赖可能连接多个区域、丢失孔洞的可视化多边形。
- 现有图像入口会按 EXIF 旋转图片。新映射入口必须明确原始像素与相机标定图像之间的关系。
- 尚未获得 JetPack/TensorRT 版本、设备连接信息、传感器型号与数据样例、相机/雷达外参、量化校准图片。本次未接入 Jetson，也未执行 GPU 或 INT8 实测。

## 可选实施范围

| 方案 | 内容 | 取舍 |
| --- | --- | --- |
| A：INT8 + 单帧局部映射（推荐） | 推理加速、时间校验、雷达投影、车体坐标、海拔接口 | 能在当前服务上逐步落地；真实映射取决于标定和同步数据 |
| B：先完成 INT8 | 只增加量化、引擎构建、对比测试；传感器接口随后实现 | 交付更集中，但不能同时验证映射链路 |
| C：扩展到全局地图 | 在 A 之上增加定位、姿态、运动补偿、跨帧关联 | 还需车辆位姿或定位系统及地图定义，当前数据不足以完成 |

以下为方案 A 的具体设计，分成可分别验收的推理加速和局部映射两个工作单元。运行中的现有接口继续兼容。

## 1. TensorRT INT8 工作单元

### 构建流程

1. 在目标 Jetson 获取 L4T、JetPack、TensorRT、CUDA、GPU PyTorch/torchvision 的实际版本，校验 CUDA NMS 和现有 FP16 模型。
2. 以已固定的原版 YOLOv5 源码导出静态 batch=1、默认 640×640 的 FP32 ONNX，明确 `images` 输入和预测/原型掩膜两个输出。
3. 使用代表性的摄像头图像进行离线训练后量化，产生含 QuantizeLinear/DequantizeLinear 的 Q/DQ ONNX。先量化经验证可支持的卷积路径，允许敏感分割分支保持浮点，记录量化配置和实际排除的层。
4. 在目标 Jetson 使用与 JetPack 匹配的 TensorRT 构建引擎。引擎加载时根据实际输入类型准备张量，不能简单把摄像头图像转换成 int8。
5. 保存引擎及 `.engine.json`，预热并检查两个输出的形状、类别数、掩膜通道数；检查量化节点和引擎精度信息。构建请求为 INT8 不等于所有层都执行 INT8。
6. 在同一图像列表上对比 PyTorch、TensorRT FP16、TensorRT INT8 的延迟与结果；提供可回切 FP16 的独立引擎文件与配置。

选择显式 Q/DQ 是为清楚记录量化位置并避免新增只依赖旧式校准器的接口。具体量化工具版本要在目标 TensorRT 版本明确后锁定；不为安装较新的工具而覆盖 JetPack 的 GPU 软件栈。NVIDIA 对 Jetson 的版本支持要求以其 [迁移说明](https://docs.nvidia.com/deeplearning/tensorrt/11.4.0/api/migration/tensorrt-10x-to-11x-jetson.html) 为准；不能把面向其他平台的 TensorRT 最新版直接当作 Jetson 安装目标。

### 校准数据与工件约束

- 校准图像用于统计量化范围，不要求每张都有标注；评价杂草识别精度另需独立、带标注的测试集。
- 校准图片应来自实际摄像头与任务场景，覆盖光照、阴影、草高、运动模糊和距离变化。可从数百张有代表性的帧起步，再根据误差调整；数量本身不保证效果。
- 校准与推理共用 RGB、letterbox、尺寸、归一化和 NCHW 处理，记录预处理版本。空目录、坏图像、尺寸配置不一致会中止量化，不使用随机图片代替真实校准数据。
- 保存模型、ONNX、数据清单和配置的摘要；缓存绑定这些摘要，变化后失效。量化校准缓存与 TensorRT 构建计时缓存分别管理。
- 不覆盖已验证的 FP16 文件。计划产物命名为 `model.fp16.engine`、`model.int8.engine` 及各自的 `.engine.json`，保存类别顺序、构建环境、量化方式和原始模型摘要。
- 当前通用 COCO 模型仍只用于部署验证；自训草坪/杂草权重替换后必须重新校准、导出和评估。

### 验收方式

- 使用固定测试图、相同输入尺寸和后处理参数，先预热再采样；计时包括必要的 GPU 同步。
- 分别记录网络推理耗时、含预处理/掩膜后处理的服务耗时、HTTP 端到端耗时，以及 p50/p95、内存、功耗模式与温度状态。
- 有标注时比较 box/mask mAP、杂草召回率、保留草坪误识别率；没有标注时只报告与浮点输出的差异，不能称为精度验证。
- 报告实际收益，不预先承诺 INT8 必定快于 FP16。若主要耗时在解码、掩膜处理或 JSON 传输，单纯量化网络可能无法明显降低整体延迟。这一测量先行的流程对应 [NVIDIA 性能实践](https://docs.nvidia.com/deeplearning/tensorrt/latest/performance/best-practices.html)。

## 2. 传感器输入与局部映射工作单元

### 数据入口

保留现有 `POST /v1/weed-segmentation`。新增计划接口 `POST /v1/scene-mapping`，采用 multipart：一张图像 `file` 和一个 JSON 文本字段 `context`。首版按单帧请求处理，采集端把对应时刻的传感器数据放入同一请求，方便回放、检查和自动测试。

| 数据 | 计划字段与含义 |
| --- | --- |
| 相机 | `camera_id`、`capture_timestamp_ns`、`clock_id`、`image_space`；标定与实际输入分辨率必须一致 |
| 雷达帧 | `radar_id`、`capture_timestamp_ns`、`clock_id`、`frame_id`、目标列表 |
| 雷达目标 | `target_id`、`coordinate_type`；三维类型提供 `position_m: [x,y,z]`，二维极坐标类型提供 `range_m` 和 `azimuth_rad`；可选 `radial_velocity_mps` 与质量字段，径向速度保留其标量含义 |
| 海拔 | `sensor_id`、时间戳、时钟、`value_m`、`reference: msl/ellipsoid/relative/unknown`、可选误差估计 |
| 标定选择 | `calibration_id`；引用本机受控配置，不接受任意文件路径 |

新 context 中的纳秒时间戳使用十进制字符串，服务内部解析并检查非负 int64 范围，以避免浏览器浮点数损失精度。旧接口的时间戳契约保持兼容。

雷达若输出距离、方位角、俯仰角，需由型号适配器转换为规范三维坐标，明确角度单位、轴方向和正负号。仅有距离/方位角而缺少俯仰信息时，不默认补 `z=0` 并冒充三维测量；返回 `insufficient_geometry`，保留原始观测用于后续适配。厂商串口/CAN/网络协议适配等待具体型号，当前不编造数据驱动。

### 时间与坐标规则

- 第一版所有参与几何关联的数据须由采集层转换到同一个 `clock_id`。不同设备的启动时间或未校准时钟即使单位同为纳秒，也不能直接相减。
- 配置允许的相机/雷达时间差，返回实际 `time_offset_ms`。默认建议先用 50 ms 做联调阈值；正式值必须按最大车速、转速和可接受位置误差确定。超差帧不做关联，第一版不静默进行运动外推。
- `base_link` 约定为车体 x 向前、y 向左、z 向上，单位米；相机光学坐标 x 向右、y 向下、z 向前。
- 用 `T_base_from_camera`、`T_base_from_radar` 明确变换方向，包含旋转和平移。检查矩阵尺寸、有限值、旋转正交性和行列式，不把任意矩阵当作标定结果。标定中的可选地面平面由单位法向量 `normal_base` 和 `offset_m` 定义，并注明适用条件；无法保证当前姿态与地面条件一致时，不使用静态平面计算落地点。
- 相机配置含 K、畸变系数、宽高及图像是否已去畸变。首版映射只接受与标定一致的图像方向；带非平凡 EXIF 旋转的输入明确拒绝，避免原有显示用旋转悄悄改变投影关系。
- 规范三维点转换和畸变投影依照 [OpenCV 相机模型](https://docs.opencv.org/4.x/d9/d0c/group__calib3d.html)。

### 映射计算与输出语义

1. 相机图像进入 YOLOv5/TensorRT，产生分割目标，同时在本次请求内保留二值掩膜。
2. 合格雷达点由雷达坐标转换到车体坐标，再转换到相机光学坐标；过滤相机后方点、非法数值和图像外点。
3. 使用内参和相应畸变模型投影到图像原始像素，不使用网络 letterbox 后的坐标。
4. 在真实二值掩膜中寻找候选关联，返回候选检测编号及关联状态。仅凭像素落入掩膜不能证明雷达反射点就是杂草的根部；多个候选保留歧义，不强行分配到一个实例。
5. 雷达点的车体位置输出为 `radar_position_base_m`，并保留投影像素与来源。它不直接覆盖检测目标的 `ground_position_m`。
6. 草坪目标的地面位置使用另一条明确的几何链路：选定图像参考像素，经去畸变反投影，与经标定且适用于当前时刻的地面平面相交。若参考像素不在掩膜内部则选取掩膜内参考点并报告它；交点须位于相机前方且在配置工作距离内。输出应标记为地面平面假设下的估计，不能直接等同刀具落点。
7. 没有有效地面平面、深度或足够标定信息时，`ground_position_m=null`。单独的绝对海拔只随响应记录，不转换成相机离地高度，也不作为像素深度。

新接口在原分割结果外增加 `mapping`，包括：

- `status: ready/partial/unavailable`、`reasons`、`calibration_id`、`output_frame_id`。
- 各传感器的时间差、是否参与关联、投影点及候选检测编号。
- `mapping.detections` 中每个检测的 `ground_position_m`、`position_method`、`reference_pixel_px` 和几何有效状态；通过检测编号关联原视觉结果，无法计算时为 null 并提供原因。旧接口的 `Detection` 类型保持兼容，新映射 schema 单独允许真实坐标。
- 原始海拔值及其参考基准；不输出未经定义的全球经纬度位置。

缺少可选传感器、不同步或缺标定时仍可返回有效视觉识别结果，并给出映射不可用原因。非法 JSON、字段类型、矩阵或非有限数值返回结构化 422；模型不可用仍为 503。首版每帧最多 256 个雷达目标，context 最多 48 KiB，图片继续使用现有大小限制；请求总大小仍由中间件约束，避免无界请求。

### 当前范围边界

摄像头采集、雷达厂商驱动、持续流缓冲、ROS 2 接入、GNSS/IMU/里程计定位、跨帧跟踪、全局建图和机械执行机构控制，均不属于本次单帧映射实现。后续可以在这套明确坐标、时钟和版本的接口上扩展。若用户选择全局地图，需先补充车辆位姿及地图原点/坐标定义，不能只靠一个海拔数值实现。

## 4. 设备信息与待用户明确的事项

在 Jetson 终端执行以下只读命令，将输出作为版本依据：

```bash
cat /etc/nv_tegra_release
dpkg-query -W nvidia-jetpack libnvinfer10 python3-libnvinfer
python3 -c "import tensorrt as trt; print(trt.__version__)"
```

某个包未安装或模块无法导入的报错也有诊断价值；先不根据报错盲目安装其他版本。已有项目环境时还可运行 `python -m scripts.check_jetson --output artifacts/jetson-environment.json`。

用户需明确：实施 A/B/C 的范围；实际 JetPack/TensorRT 版本；海拔是绝对高度还是离地高度；雷达目标是否含三维坐标。设备连接、传感器样例和标定数据未提供之前，可以实现离线契约与几何测试，真实设备关联与性能验收保持未完成状态。
